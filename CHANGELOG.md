## 14 Oct 2026 — Book through the database

- **Why:** on 14 Oct 2026 at 10:00 the group opened booking and thirty-six phones tapped at once. Every tap uploaded the whole 0.6 MB document with a compare-and-swap, lost, downloaded it, retried six times and gave up ("Too many people booking at once"); a server error on any attempt kept the pick on the phone as "saved on this device" and merged it later unchecked; and Realtime, broadcasting the whole document to every phone on every save, collapsed (statement cancellations, replication slot lost 10:07–10:41), so phones stopped seeing each other and tapped zones already taken. `docs/operations/INCIDENT-2026-10-14-booking-storm.md` has the evidence; `docs/superpowers/specs/2026-10-14-book-through-the-database-design.md` the decisions.
- **A booking is a database call** (`supabase/prod-booking-rpc.sql`, pasted by the owner AFTER this build is live): `roster_commit(org, cycle, ops)` locks the group's row so writers queue instead of racing, judges each op against the roster as it is at that instant — the day in the cycle, the person on the roster, nothing already on their day, no approved leave, the zone open in that half and not held by a colleague in an overlapping half (a whole-day shift needs both), the half under its cap `min(maximum, zones open)` — writes the one key with `jsonb_set`, puts the audit row first, writes one `roster_events` row per applied op, bumps `updated` to the server clock, and answers per op in the app's own words. Share, period targets, fatigue, waves, the round gate and the notice period stay on the phone as dry runs before the call. An unbook goes the same way (never a fixed shift from a staff member).
- **The phone never pretends:** a pick goes on the screen at once; a refused pick comes off with the server's reason, and if the call never arrives every pick comes off — "Couldn't reach Myrosta — that tap wasn't saved. Check your signal and try again." No "saved on this device" for a booking. The merge token (`updated`) is not adopted from the call, so the phone's next whole-document save fails its swap and merges, which is the only safe thing a stale document can do.
- **Changes travel as events:** Realtime now carries `roster_events` rows (about 300 bytes) and a one-row `org_events` ping for whole-document saves (a trigger on `org_state`, silent for the call's own writes); `org_state` leaves the publication. Phones apply events to the live roster and to the merge base (so a missed event can never resurrect a removed shift), de-duplicate audit rows by id, remember the last `seq`, and catch up fifty events back — on a refusal, on (re)subscribe, when the screen or the network comes back, and every 45 s — with a jittered single refetch when a ping says the document itself changed.
- **Both schemas:** the app probes `roster_events` at load; without it (SQL not yet pasted) every path is exactly as before, and the About row under More reads "bookings go straight to the database" once the call is there. Side fix in the same SQL: the server key may read the group registry (the reminder cron's "permission denied for table orgs").
- **Second push, same afternoon (after the SQL ran on production — the live site, the table, the function and the publication were verified from here):** the bell no longer saves the whole document when notifications are opened (the marks are kept on the device and ride up with the next natural save; `notifRead`); a whole-document save that loses its swap waits 4–12 s and tries again instead of giving up, and tries twice rather than five times while bookings are flowing; the live-update channel reports its state in the About row ("live updates on" / "off — checked every 45 s instead") and, if the server refuses the group filter, listens without it, since row-level security already keeps other groups' rows away.
- **The booking page, after the owner's first look at it on a wide screen (same evening):** the day list names each month where it begins — "November 2026" above the 1st, and the cycle's own month above the first row — because a bare "Tue 1" said nothing about where in the cycle it was (`monthRowHTML`, `.daylist .monthrow`); and on a wide screen every sheet (the day sheet, requests, notifications, More) is a centred dialog instead of a drawer hugging the bottom edge, which read as half the screen gone.
